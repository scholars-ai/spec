# SPEC-004 · 评分体系（Evaluation）

- 状态：Superseded（评分原则保留；运行判定与回放以 SPEC-010 为准）
- 日期：2026-08-06
- 依赖：SPEC-002, SPEC-003, SPEC-005

评分体系是本项目的核心竞争力，也是最容易做成"拍脑袋 prompt"的地方。本 spec 的立场：**评分 = 版本化的 rubric + LLM-as-Judge + 规则信号 + 用真实数据持续校准的权重**。每次评分属于 `WorkflowRun` 的 `topic_evaluate` 或 `article_evaluate` 节点，必须生成结构化 `WorkflowItemDecision`；拒绝、跳过、失败及原因不能只存在于日志。

## 1. 通用设计

所有评分（选题/文章）共享同一套机制：

1. **Rubric 版本化**：rubric（维度定义、评分标准、few-shot 锚定样例、权重）以 `scholar-shared` 中受 Schema 约束的 YAML 数据文件存在，使用语义化版本号（如 `topic@v2`、`article/zhihu@v3`）。每次评分记录 rubric_version，历史分数永远可解释、可回放。
2. **维度分 + 加权总分**：每个维度 0–10 分并要求给出理由，总分 = Σ(维度分 × 权重) 归一化到 0–100。**权重独立于 rubric 文本，存 DB，可被校准环节调整而不动 prompt**。
3. **锚定样例（calibration anchors）**：每个维度配"3 分长这样 / 7 分长这样 / 9 分长这样"的真实样例，抑制 LLM 评分的中心化倾向。样例池随数据积累从真实高/低表现内容中更新。
4. **评审独立性**：Judge Agent 与 Writer Agent 是不同的 prompt/角色，Judge 看不到"这是谁写的"，只看内容 + rubric。
5. **留痕**：每次评分挂 Langfuse trace + agent_runs，理由（rationale）必须人可读——评分不可信时，人要能一眼看出是 rubric 问题还是模型问题。

## 2. 选题评分（历史 v1；当前版本由 shared rubric registry 决定）

| 维度 | 初始权重 | 评什么 |
|---|---|---|
| timeliness 时效性 | 0.20 | 热点窗口期？常青话题不扣分但标注类型 |
| audience_value 受众价值 | 0.25 | 对目标读者（AI 学习者/从业者）有多大信息增量或情绪价值 |
| platform_fit 平台适配 | 0.15 | 该角度在建议平台上有没有成立的内容形态 |
| differentiation 差异化空间 | 0.15 | 全网已有内容饱和度，我们能不能提供不同视角 |
| material_richness 素材支撑 | 0.10 | 现有素材够不够写出干货，还是只有一句新闻 |
| history_signal 历史信号 | 0.15 | 与历史高表现选题的相似度（embedding 检索 + 表现数据），冷启动阶段此维度权重自动降为 0 并按比例归一 |

- 规则信号辅助：信源 weight、素材被多信源交叉报道次数，作为结构化上下文喂给 Judge，而不是 Judge 自己瞎猜热度。
- 输出分档：阈值、权重和 rubric 版本必须从本次运行配置快照读取并原样记录；通过的全部 topic 进入后续写作，不得按固定数量截断。低于阈值的 topic 记录 `rejected` 及 reason code，技术异常记录 `failed`，资源保护记录 `skipped/deferred`。

## 3. 文章评分（article rubric，按平台分叉）

通用维度（所有平台共享）：

| 维度 | 评什么 |
|---|---|
| accuracy 事实准确 | 与素材事实一致，无编造；技术表述正确 |
| structure 结构 | 开头钩子、行文逻辑、结尾引导 |
| readability 可读性 | 语言流畅度、段落节奏、术语解释是否到位 |
| format_compliance 格式合规 | Markdown 规范、字数区间、平台硬性要求（见 SPEC-005 各平台约束） |

平台特化维度（示例，权重在各平台 rubric 中定义）：

- **小红书**：标题吸引力（20 字内、有情绪价值/利益点）、口语化程度、emoji 与分段密度、种草感/实用清单感
- **知乎**：论证深度、专业可信度（引用/数据支撑）、开头是否直接回应问题、反直觉观点的处理
- **公众号**：标题打开率潜力、叙事完整性、金句密度、排版节奏（小标题/引用块分布）

流程接入（对应 Article 状态机）：ArticleJudge 只输出每维分数、理由和总体理由；生效权重版本、总分、veto 和 `passed` 由确定性代码计算并随评分记录固化。通过的全部文章进入 `human_review`；未通过的文章记录具体维度短板和修改建议，并按运行策略决定是否创建下一不可变版本。回炉上限是资源/策略配置，不得把未处理项静默丢弃。

**事实准确维度单独处理**：accuracy < 6 一票否决直接回炉，不参与加权平均——数据再好看的文章，事实错了就是事故。

## 4. 校准闭环（本体系的灵魂）

评分的终极标准不是 Judge 觉得好，而是**真实数据证明好**。校准环节（M3 起）：

```
每周校准 job：
1. 取近 N 周有 metric_snapshots 的文章，计算表现分 P（平台内归一化，见 SPEC-006 §3）
2. 计算：topic 总分 vs P 的相关性、article 总分 vs P 的相关性、各维度分 vs P 的相关性
3. 产出校准报告（client 可见）：
   - 哪些维度预测力强 → 建议加权重
   - 哪些维度与结果无关甚至负相关 → 建议降权重或修 rubric 定义
   - 高分低表现 / 低分高表现的 case 列表 → 交给反思 Agent 归因（SPEC-006）
4. 权重调整先人工确认后生效（记录为新的权重版本）；锚定样例从真实 top/bottom case 中补充
```

冷启动策略：前 ~30 篇文章数据积累期，权重不动，只积累"预测 vs 实际"配对数据。样本量不足时校准报告明确标注置信度低，避免过拟合到偶然爆款。

## 5. 验收标准（历史里程碑与当前运行约束）

当前运行层验收以 SPEC-010 §4、§9 为准：每个评估 item 都要有 `accepted`、`rejected`、`skipped` 或 `failed` 判定；reason code、可读理由、实际阈值/权重/rubric 版本和输入证据必须可回放；技术失败与业务拒绝必须在节点状态和统计中分离。

- [ ] M1：选题评分上线，人工抽查 20 条，评分理由认可率 ≥ 80%
- [x] M2 工程闭环：三平台文章评分、确定性判定和不可变版本回炉可用；跨仓库 E2E 中回炉文章 v1 58.5 → v2 80
- [ ] M3：首份校准报告产出，包含相关性分析和 case 归因
- [ ] M4：完成 ≥2 轮权重校准，topic 总分与实际表现的相关性较初始提升（量化记录）

## 6. 开放问题

- [ ] 多 Judge 投票（3 次采样取中位数）能显著降方差但 3 倍成本，M2 用数据决定
- [ ] 表现分 P 中不同指标（阅读/点赞/收藏/转发）的权重按平台目标定义，需在 SPEC-006 细化
